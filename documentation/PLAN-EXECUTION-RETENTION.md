# PLAN-EXECUTION-RETENTION — execution history retention and blob reclamation

Source: `FIX-EXECUTION-RETENTION.md` (security/bug audit finding #10, plus the
`deserializeSnapshot` silent-`""` fallback).

## 1. Problem

Nothing in this codebase has ever deleted an execution, branch, snapshot, step, response, run
event, state row, context, message, or blob. `releaseBlob` (`packages/persistence/src/blobs.ts:29`)
has zero call sites; `putBlob` only ever increments. Execution history is append-only forever.

Blob GC is the *second* problem. The first is that there is no retention unit at all, so blob
reclamation has nothing to hang off.

### 1.1 Facts that shape the design

- **No `ON DELETE CASCADE` anywhere.** All 38 FK clauses in the migrations are
  `ON UPDATE no action ON DELETE no action`, and `openDb` (`packages/persistence/src/db.ts:16`)
  sets `PRAGMA foreign_keys = ON`. Delete order is mandatory; a mistake throws loudly rather than
  silently orphaning. Keep it that way — never reach for `defer_foreign_keys`.
- **There is no FK cycle.** `branches.forked_from_snapshot_id` and `snapshots.parent_snapshot_id`
  carry *no* FK (verified against `migrations/0000_futuristic_banshee.sql:9-17,154-163`).
  `CLAUDE.md` currently claims a circular `branches`↔`snapshots` relationship; that note is wrong
  and is corrected as part of this work.
- **Seven columns FK to `blobs.sha256`:** `messages.content_sha`,
  `responses.{rendered_prompt_sha,thinking_sha,content_sha}`, `tool_calls.result_sha`,
  `state_writes.value_sha`, `execution_triggers.payload_sha`.
- **`snapshots` is the eighth, invisible root.** Its blob refs live inside the opaque
  `payload_json` column as `{kind:"value", ref:"<sha>"}` entries produced by `serializeSnapshot`
  (`packages/server/src/stepper.ts:28`). **An FK-walking sweep will delete every blob a step-debug
  session depends on.** This is the single most likely data-loss bug in this work.
- **`run_events.payload_json` never embeds a sha.** Snapshots are the *only* invisible root, which
  bounds the problem.
- **`messages` has no execution column.** It is reachable only via `context_messages → contexts`.
- **`execution_triggers.execution_id` is the primary key.** The row cannot outlive its execution.
- **Refcounts are garbage in both directions.** `putBlob` increments; `releaseBlob` never runs
  (overcount); and `stepBack` (`packages/server/src/stepper.ts:167-172`) copies a snapshot payload
  verbatim into the fork's new row *without* `putBlob` (undercount). Existing values mean nothing.
- **Snapshots are step-mode only.** `runFlow` (`packages/server/src/executor.ts`) writes none.
- **Zero indexes on FK child columns.** Existing indexes are only `flow_versions(flow_id,version)`,
  `flow_versions_content_idx`, `run_events(execution_id,seq)`, `snapshots(branch_id,step_index)`,
  `steps(branch_id,step_index)`, `execution_triggers(external_id)`.
- **No transaction is used anywhere in the repo today.** This is the first place one is needed.

## 2. Locked decisions

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | **Retention unit is the whole execution.** | Sub-execution snapshot reclamation is a real, separate design (see §9). |
| D2 | **Policy is age-only: 30 days.** No `keepNewest`. | A flow version is unrecoverable source, so `gcFlowVersions` guards it with a count; an execution is a reproducible log. |
| D3 | **Mark-and-sweep, scoped to candidate shas.** Never a whole-table blob scan. | No migration to recompute refcounts, tolerates the historical garbage, robust to a missed decrement — and scoping keeps unrooted `SqliteBlobStore` blobs safe by construction. |
| D4 | **Runs once at boot, then on a 24h timer.** | Boot alone misses a long-lived Discord-trigger server; a timer alone never fires on a server restarted more often than daily. |
| D5 | **`execution_triggers` rows are deleted with their execution.** | §5. |
| D6 | **`refcount` column and `releaseBlob` are removed.** | A field that lies is worse than no field; removing it turns `WHERE refcount = 0` into a compile error. |
| D7 | **Surface: persistence + timer + CLI.** No HTTP routes. | §8. |
| D8 | **Executions first, flow versions second**, always. | §6. |

## 4. Implementation

### S1 — Fail loudly first (do this before any deletion code exists)

Three silent fallbacks become throws. Until they do, a GC bug corrupts a run instead of erroring.

- `packages/server/src/stepper.ts:50` — `deserializeSnapshot` currently does
  `value: bytes ? bytes.toString("utf-8") : ""`. Throw, naming the sha and the `nodeId.port`.
- `packages/persistence/src/state.ts:105` (`listStateWritesForBranch`) and **`:156`
  (`getStateSnapshotAsOf`)** — both do `bytes ? JSON.parse(...) : undefined`. `:156` is on
  `stepBack`'s path, so a GC bug there silently seeds a forked branch with `undefined` state.
  The FIX doc only names `stepper.ts:50`; fixing just that one covers a third of the exposure.

### S2 — `withTransaction` and pragmas (`db.ts`)

Do **not** use `db.transaction(fn)`: drizzle hands the callback a `SQLiteTransaction<...>` that is
not assignable to this repo's `Db`, so every helper (`putBlob`, `getBlob`, …) fails typecheck
inside it. Go through the underlying client instead, keeping the `Db` type:

```ts
/** better-sqlite3's own transaction wrapper, driven through drizzle's underlying client so
 *  drizzle query builders on the same `Db` participate. Unlike `db.transaction(fn)` this keeps
 *  the `Db` type, so every existing helper works unchanged inside it. Re-entrant (better-sqlite3
 *  falls back to SAVEPOINT). `.immediate()` takes the write lock up front so a concurrent writer
 *  — the CLI running against a live server's DB — fails fast rather than deadlocking on a
 *  deferred-to-write upgrade. */
export function withTransaction<T>(db: Db, fn: () => T): T {
  return db.$client.transaction(fn).immediate();
}
```

Also add `sqlite.pragma("busy_timeout = 5000")` to `openDb`. Once `flowlathe gc` exists it can run
against a live server's WAL-mode DB; with no busy timeout that is an immediate `SQLITE_BUSY`.

### S3 — `deleteExecution(db, executionId)`

```ts
export interface DeleteExecutionResult {
  executionId: string;
  rowsDeleted: number;
  blobsDeleted: number;
  bytesReclaimed: number;
}
```

Everything below runs inside **one** `withTransaction`.

**Phase A — collect candidates before deleting anything.** Use correlated subqueries, never
`inArray` over materialized id lists (a long step session has thousands of `steps`/`responses` ids
and would hit `SQLITE_MAX_VARIABLE_NUMBER`). Collect into a `Set<string>`:

- `responses.{rendered_prompt_sha, thinking_sha, content_sha}` where `execution_id = ?`
- `tool_calls.result_sha` where `response_id IN (responses of this execution)`
- `state_writes.value_sha` where `branch_id IN (branches of this execution)`
- `messages.content_sha` where `id IN (context_messages ⋈ contexts of this execution)`
- `execution_triggers.payload_sha` where `execution_id = ?`
- **`snapshots.payload_json`** where `branch_id IN (branches of this execution)`, via
  `collectSnapshotBlobRefs`

Also capture the **message ids** from the same join, before Phase B destroys the join path.

```ts
/** Every blob sha reachable inside a snapshot's opaque `payload_json`. Walks the whole tree for
 *  any object with a string `ref`, rather than assuming the current
 *  `{outputs:{node:{port:slot}}}` shape — if `serializeSnapshot`
 *  (packages/server/src/stepper.ts:28) ever nests refs somewhere else, this keeps finding them.
 *  Over-collecting keeps a blob alive; under-collecting deletes live data. Always over-collect. */
export function collectSnapshotBlobRefs(payload: unknown, into: Set<string>): Set<string>
```

Note `snapshots.payloadJson` is drizzle `text(..., {mode:"json"})`, so a select returns the
**already-parsed object** — `collectSnapshotBlobRefs` takes `unknown` and walks it; there is no
second parse and nowhere to get escaping wrong.

**Phase B — delete rows, child-first.** Fourteen statements, each a single correlated-subquery
delete. `brQ = SELECT id FROM branches WHERE execution_id = ?`,
`ctxQ = SELECT id FROM contexts WHERE execution_id = ?`.

| # | Table | Predicate |
| --- | --- | --- |
| 1 | `tool_calls` | `response_id IN (SELECT id FROM responses WHERE execution_id = ?)` |
| 2 | `responses` | `execution_id = ?` |
| 3 | `context_transform_calls` | `source_context_id IN ctxQ OR result_context_id IN ctxQ` |
| 4 | `context_messages` | `context_id IN ctxQ` |
| 5 | `messages` | *scoped orphan check, below* |
| 6 | `state_writes` | `branch_id IN brQ` |
| 7 | `state_reads` | `branch_id IN brQ` |
| 8 | `steps` | `branch_id IN brQ` |
| 9 | `snapshots` | `branch_id IN brQ` |
| 10 | `run_events` | `execution_id = ?` |
| 11 | `execution_triggers` | `execution_id = ?` |
| 12 | `contexts` | `execution_id = ?` |
| 13 | `branches` | `execution_id = ?` |
| 14 | `executions` | `id = ?` |

Ordering constraints: 1 before 2; 2 before 8, 12, 13; 3–5 before 12; 6–9 before 13.

**Step 5, the `messages` problem.** `messages` has no execution FK. Use a *scoped* orphan check —
the same shape as the blob sweep, one level up — run after step 4:

```sql
DELETE FROM messages
 WHERE id IN (:messageIdsCollectedInPhaseA)
   AND NOT EXISTS (SELECT 1 FROM context_messages cm WHERE cm.message_id = messages.id);
```

The `NOT EXISTS` guard is a no-op today (`materializeMessage`, `contexts.ts:8-13`, mints a fresh
uuid per message even for identical content, and `materializeContext` is only ever called with one
execution's id). Write it anyway: it is the only thing standing between a future
dedupe-messages-by-content-hash optimization and cross-execution data loss, and it costs one
indexed lookup per candidate. **Never** write the unscoped version
(`DELETE FROM messages WHERE id NOT IN (SELECT message_id FROM context_messages)`) — that is a
whole-table orphan sweep and would eat any message row a future writer creates before wiring its
`context_messages` row.

**Phase C — scoped blob sweep.** Runs after Phase B, so this execution's own snapshots are already
gone and can't keep their own blobs alive.

*C.1 — subtract surviving snapshot refs.* Page through remaining snapshots (ordered by `id`, 500
at a time), run `collectSnapshotBlobRefs` on each payload, and `candidates.delete(sha)` for each
ref found. Stop early once `candidates` is empty.

> Deliberately *not* done in SQL. `json_tree(payload_json) WHERE key='ref'` works (SQLite 3.53.4
> with JSON1 is what `better-sqlite3@13.0.3` ships) and is a legitimate optimization later — but
> only if it replaces the TS walker in *both* directions. Two implementations of "what refs does a
> snapshot payload contain" diverge asymmetrically in the fatal direction: a ref the walker finds
> (making it a candidate) but the SQL misses (making it look dead) is a deleted live blob.

*C.2 — delete what's left, if no FK column still points at it.* Batch at 500 shas per statement:

```sql
DELETE FROM blobs WHERE sha256 IN (…batch…)
  AND NOT EXISTS (SELECT 1 FROM messages m           WHERE m.content_sha         = blobs.sha256)
  AND NOT EXISTS (SELECT 1 FROM responses r          WHERE r.rendered_prompt_sha = blobs.sha256)
  AND NOT EXISTS (SELECT 1 FROM responses r          WHERE r.thinking_sha        = blobs.sha256)
  AND NOT EXISTS (SELECT 1 FROM responses r          WHERE r.content_sha         = blobs.sha256)
  AND NOT EXISTS (SELECT 1 FROM tool_calls t         WHERE t.result_sha          = blobs.sha256)
  AND NOT EXISTS (SELECT 1 FROM state_writes w       WHERE w.value_sha           = blobs.sha256)
  AND NOT EXISTS (SELECT 1 FROM execution_triggers e WHERE e.payload_sha         = blobs.sha256);
```

Three columns of `responses` get three separate `NOT EXISTS`, not one with `OR` — an `OR` across
three columns cannot use a single-column index and degrades to a full scan per candidate. And it
is an explicit `NOT EXISTS` chain rather than "try the delete, catch the FK error", because the
latter aborts the enclosing transaction on the first live blob.

`bytesReclaimed` = `SELECT sum(byte_len) … WHERE sha256 IN (survivors)` immediately before.

### S4 — `gcExecutions` / `gcAllExecutions` / `gcFlowHistory`

```ts
export interface ExecutionGcOptions {
  /** Only an execution whose `endedAt ?? startedAt` is older than this is eligible.
   *  FLOWLATHE_EXECUTION_GC_OLDER_THAN_DAYS, else 30. */
  olderThanDays?: number;
  /** A `running`/`awaiting_input` execution is only eligible once it is this old — nothing in
   *  this repo reconciles a crash-orphaned status, so such a row would otherwise be immortal.
   *  FLOWLATHE_EXECUTION_GC_ABANDONED_AFTER_DAYS, else 7. */
  abandonedAfterDays?: number;
}
```

Copy `flow-version-gc.ts:19-24`'s `envInt` helper (or lift it to a shared `env.ts`). Guard chain,
one `continue` per line with a comment, exactly like `flow-version-gc.ts:57-68`:

1. `status` is `running` or `awaiting_input` **and** `startedAt` newer than the abandoned cutoff
   → keep. *(A step-mode session idle between steps has status `running` —
   `host-builder.ts:80` — so this is what protects an open debugging session. At the default
   30-day cutoff this guard never bites; it exists for the CLI's `--older-than-days 0` path.)*
2. `(endedAt ?? startedAt)` newer than the cutoff → keep.
3. otherwise → `deleteExecution`.

**Nothing outside the subtree points at an execution.** `grep '.references(() => executions.id)'`
yields exactly `branches`, `contexts`, `responses`, `run_events`, `execution_triggers` — no
`flow_pins`, `triggers`, or `flow_versions` row ever references one. Say so in the docstring so the
next reader does not re-derive it. There is deliberately **no `keepNewest` guard** (D2) and no
`protectIds` set: `ExecutionHub` has no reliable live-execution list (a run with no SSE subscriber
has no entry), and a 30-day cutoff already puts every live execution out of reach.

`gcAllExecutions(db, opts)` iterates `flows` and calls `gcFlowHistory` per flow.

```ts
/** Retention for one flow's whole history, in the only order that makes progress: executions
 *  first (a live execution is a `gcFlowVersions` keep-reason — flow-version-gc.ts:52), then the
 *  versions those executions were pinning. The other order collects nothing on the first pass.
 *  This — not `gcExecutions` — is what callers reach for. */
export function gcFlowHistory(db: Db, flowId: string, opts?): { executions; versions }
```

Keep the composition *out of* `gcExecutions` so each GC stays independently testable and the
import graph stays one-way (`execution-gc.ts → flow-version-gc.ts`, never back). `flows.ts:238`
keeps calling `gcFlowVersions` alone — a save is not a reason to reconsider executions.

Log only when something was collected, matching `flow-version-gc.ts:70-72`:
`[execution-gc] collected N execution(s), M blob(s), K MB from flow X`. A boot sweep that silently
deletes 40k blobs is the thing you will wish you had logged.

### S5 — migration 0006

Declare the indexes in `schema.ts`'s third-argument arrays and the `refcount` drop, then run
`pnpm db:generate` in `packages/persistence`. Never hand-write the `.sql` — `meta/_journal.json`
desyncs.

**Tier 1, children of `blobs`** — every blob delete pays FK verification against each of these,
and with no index that verification is a **full table scan of the child table per deleted row**:
`responses(rendered_prompt_sha)`, `responses(thinking_sha)`, `responses(content_sha)`,
`messages(content_sha)`, `state_writes(value_sha)`, `tool_calls(result_sha)`,
`execution_triggers(payload_sha)`. Without these, GC does not merely run slowly on a big DB — it
does not finish on exactly the DB that needed it.

**Tier 2, children of the subtree parents:** `branches(execution_id)`, `responses(execution_id)`,
`contexts(execution_id)`, `responses(branch_id)`, `run_events(branch_id)`,
`state_writes(branch_id)`, `state_reads(branch_id)`, `responses(step_id)`,
`state_writes(step_id)`, `state_reads(step_id)`, `context_transform_calls(source_context_id)`,
`context_transform_calls(result_context_id)`, `responses(request_context_id)`,
`context_messages(message_id)`.
*Already covered, deliberately omitted:* `steps(branch_id)` / `snapshots(branch_id)` by their
composite indexes, `run_events(execution_id)` by its unique, `context_messages(context_id)` and
`execution_triggers(execution_id)` by their primary keys.

**Tier 3, children of `flow_versions`** — a latent version of the same problem in the GC that
already ships: `executions(flow_version_id)` (also what the per-flow listing rides on),
`triggers(flow_version_id)`, `flow_pins(flow_version_id)`.

Write cost is a handful of extra index updates per `responses` insert — irrelevant next to an LLM
round trip.

**`refcount` drop.** Remove the column from `schema.ts`, stop writing it in `putBlob`
(`blobs.ts:15,18`), and delete `releaseBlob` (`blobs.ts:29-34`) outright — it is exported through
`index.ts` with zero call sites repo-wide. **Inspect the generated SQL before committing:** it
should be ``ALTER TABLE `blobs` DROP COLUMN `refcount`;`` (SQLite ≥3.35; we are on 3.53.4). If
drizzle-kit instead emits a `__new_blobs` table rebuild, **do not ship it** — that copies every
blob byte, doubling disk and taking minutes on the very DB you are trying to shrink; hand-edit the
`.sql` down to the `ALTER` form, leaving `meta/0006_snapshot.json` as generated.

Worth noting in the commit message: mark-and-sweep makes the `stepBack` undercount bug
(`stepper.ts:167-172`) *disappear* rather than get fixed — the copied refs are found by
`collectSnapshotBlobRefs` like any other, and there is no counter left to be wrong.

### S6 — the timer (`packages/server/src/retention.ts`)

Mirror `watchFlowsDir`'s shape: a start function returning a stop function.

```ts
export interface RetentionTimerOptions {
  db: Db;
  /** FLOWLATHE_EXECUTION_GC_INTERVAL_HOURS, else 24. */
  intervalHours?: number;
  /** Delay before the first sweep, so `listen()` isn't blocked. Default 30_000. */
  initialDelayMs?: number;
}
export function startRetentionTimer(opts: RetentionTimerOptions): () => void
```

- One sweep shortly after boot (`initialDelayMs`), then `setInterval(intervalHours * 3600_000)`.
- Both timers `.unref()`, so a pending sweep never holds the process open.
- Each sweep is `gcAllExecutions(db)` wrapped in try/catch — a GC failure logs and the timer keeps
  running; it must never take the server down.
- Wire in `packages/server/src/index.ts` alongside `watchFlowsDir` (around line 126), and clear it
  in the SIGINT/SIGTERM handler next to `stopWatchingFlows`.

The boot sweep is what handles an upgrade onto a large existing DB, a policy change via env, and a
flow that stopped running entirely; the interval is what handles a server that stays up for weeks
with a Discord trigger firing all day.

### S7 — `flowlathe gc`

```
flowlathe gc [--db <path>] [--flow <id>] [--dry-run]
             [--older-than-days D] [--abandoned-after-days D] [--vacuum]
```

Follow `commands/flows.ts`: `parseArgs` from `src/args.ts`, `options.get("db") ?? requireDbPath()`,
`openDb` + `runMigrations` + `finally { opened.close() }`, return `0`/`1`. Register in
`cli.ts`'s switch, the `USAGE` string, and `src/index.ts`.

Three things it does that the server hooks cannot:

- **`--dry-run`** — run the real guard chain and report `{executions, blobs, bytes}` per flow
  without deleting. Implement by running the real transaction and throwing a sentinel at the end to
  force rollback, catching it in the caller. Ugly but honest, and far safer than a parallel
  counting path that can drift from the real one.
- **`--vacuum`** — **only** here, never on the server or boot path. `VACUUM` cannot run inside a
  transaction and rewrites the whole file. Without it SQLite keeps freed blob pages in the free
  list and **the file never shrinks**, which is the first thing you will notice after the first big
  sweep. `auto_vacuum=INCREMENTAL` is not retroactively settable, so an explicit CLI `VACUUM` is
  the only path.
- Running against a stopped server, or a copy of the DB, without a restart.

## 5. `execution_triggers` and the Discord dedupe claim

`execution_triggers.external_id` UNIQUE **is** the Discord redelivery dedupe claim, and
`execution_id` is the primary key — the row cannot outlive its execution. **Decision: delete it
with the execution.** The argument, from the actual recovery code:

- The post-reconnect scan (`packages/server/src/triggers/discord.ts:82-99`) is triple-bounded: it
  starts at `after: cursor` (`getTriggerCursor`, skipping a channel entirely with no cursor), is
  clamped to `recoveryWindowSeconds` (**default 900**, `:88`) and to `recoveryLimit` (**default
  50**, `:89`). A message older than 15 minutes is structurally unreachable.
- Gateway RESUME replays only events missed since the session's last sequence number — minutes.
- `trigger_cursors.last_message_id` advances monotonically on admission, so the window slides
  permanently past collected messages.

So a claim whose execution is 30 days old has zero remaining dedupe value; its job finished long
before retention looked at it. The alternative (a `trigger_claims(external_id PK, …)` table
decoupled from `executions`) would preserve exactly the worthless part while *not* preserving what
`PLAN-INTEGRATIONS.md:644` actually cares about — provenance, which is inherently execution-scoped.

Two safeguards that make this cheap to be right about:

1. State the coupling in the code comment: *`olderThanDays` must stay comfortably above
   `recoveryWindowSeconds` (`discord.ts:88`, default 900s) — that window is the only thing that can
   re-present a collected `external_id`.*
2. It is the strongest reason not to ship `DELETE /api/executions/:id` (§8): an explicit,
   age-bypassing delete of a two-minute-old triggered execution is the one operation that can
   genuinely resurrect a duplicate Discord post.

Add one line to `PLAN-INTEGRATIONS.md`'s Retention section noting that `execution_triggers` rows
are collected with their execution, and why. Its "keep them" is correct within its own scope (do
not prune them on *its* schedule); execution retention is a strictly outer policy.

## 6. Ordering with `gcFlowVersions`

The coupling is one-directional: `gcFlowVersions` treats an execution as a **reason to keep** a
flow version (`flow-version-gc.ts:52`), so execution GC is what **unblocks** flow versions. The
reverse never holds. Therefore **executions first, versions second**, at every trigger point —
which is what `gcFlowHistory` encodes.

This matters concretely: `gcFlowVersions`'s only call site today is inside `saveFlowVersion`
(`flows.ts:238`), so a trigger-driven flow that is never edited never runs version GC at all. Its
ancient flow versions stay pinned forever by ancient executions that this work just collected. The
boot/timer sweep going through `gcFlowHistory` is what finally closes that.

### Cases

**Subtree deletion**

1. `deleteExecution` empties all 13 tables for that execution — driven off a table list, so nobody
   can quietly forget one when a 14th table is added.
2. A second, untouched execution keeps every one of its rows.
3. `expectIntegrity` passes (assert explicitly here, naming it as the definition-of-done item).
4. Deleting the same id twice is a no-op, not a throw.

**Blob liveness**

5. **Shared blob survives** *(FIX doc mandate)*. Two executions `recordResponse` identical content
   → one `blobs` row. Delete A; the blob survives and B's `content_sha` still resolves.
6. **Snapshot-payload-only reference honoured** *(FIX doc mandate)*. A sha referenced by a
   `responses` row in execution A **and** only-by-snapshot-payload in execution B. Delete A — the
   blob must survive. *This is the version that matters:* a naive "snapshot ref survives" test
   passes even against a broken FK-only sweep, because the sha never becomes a candidate. This one
   passes only if Phase C.1 actually parses remaining payloads.
7. **Converse.** A blob referenced *only* from A's own snapshot payload (no FK row anywhere) **is**
   collected when A is deleted — proving Phase A parses the dying payloads, and that a pure-FK
   candidate collection would leak.
8. **Cross-branch within one execution.** `stepBack` forks and copies the payload verbatim
   (`stepper.ts:171`); delete a *different* execution and assert both branches' refs survive.
9. **Unrooted blob.** `new SqliteBlobStore(db).put(bytes)` with unique content survives deleting an
   execution. Then the documented-hazard twin: `put()` with content byte-identical to a deleted
   execution's response **is** collected. Assert the current behaviour with a comment pointing at
   the `sqlite-blob-store.ts` note, so the trade-off is pinned rather than rediscovered.

**Contexts / messages**

10. `recordContextCompaction` into A, delete A → `contexts`, `context_messages`,
    `context_transform_calls`, `messages` all zero, and the message-content blobs collected.
11. Same content compacted into B as well → B's `messages` rows and the shared content blob
    survive deleting A.

## 8. Scope: what is deliberately not built

- **`listExecutionsForFlow`** — built, because `gcExecutions` needs "this flow's executions, newest
  first" via a join through `flow_versions`. Exported rather than kept private: it is the natural
  seed for a future history UI and costs nothing.
- **`GET /api/executions`** — **not** built. There is no consumer: `packages/web/src/pages/
  Canvas.tsx` tracks only the in-page session and there is no history view to feed. Also
  `routes/executions.ts` is currently owned by `HANDOFF-QUICK-FIXES.md` item 9, so adding routes
  there guarantees a conflict. Obvious follow-up, in the same change as whoever builds the UI.
- **`DELETE /api/executions/:id`** — **not** built, and not only for scope: it is the one operation
  that can defeat the Discord dedupe claim inside its live window (§5). If it is ever added it must
  refuse `running`/`awaiting_input` and refuse an execution younger than the recovery window.

## 9. Known, deliberately unhandled

**Whole-execution retention does nothing for growth *within* one open step session.** Step mode
writes a snapshot per step, each with one blob per port value. A user 400 steps into a debugging
session is the single largest contributor to DB growth, has status `running`, and is protected by
every guard — correctly, since `stepBack` can target any snapshot. Whole-execution is still the
right unit for v1; a partial-snapshot policy would have to reason about which snapshots remain
reachable as step-back targets, which is real design work. The honest story to record: **bounded
across executions, unbounded within one open step session.**

## 10. `CLAUDE.md` notes (definition-of-done)

Three, not one:

1. **Snapshot blob refs are not FKs.** `snapshots.payload_json` embeds `{kind:"value", ref:"<sha>"}`
   (`stepper.ts:28`). Any GC walking foreign keys alone deletes every blob a step session depends
   on. `collectSnapshotBlobRefs` is the single source of truth — use it for both "what is dying"
   and "what survives", or the two drift apart in the fatal direction.
2. **`SqliteBlobStore.put()` produces unrooted blobs.** Nothing calls it today; the first caller
   must root the returned sha in a row GC can see, or add a root to the liveness check. Because
   blobs are content-addressed, a `put()` of bytes identical to a collected execution's value is
   the *same row* and will be collected out from under it. Mirror this as a comment at
   `sqlite-blob-store.ts:8`.
3. **Correction:** `branches.forked_from_snapshot_id` and `snapshots.parent_snapshot_id` carry no
   FK. The existing "circular FK relationship" note is wrong — there is no cycle in the delete
   order, and no reason to fear one.
